How packages work

A package (bouquet) is a named bundle of channels granted as one unit — assign it on the Users tab (the + grant dialog or a package chip's ✕). Grants stay cryptographic: every change here is materialized into per-user sealed keys immediately; clients pick new ones up at their next login. Members can be stream ids, id globs (sports-*), or selectors category:<slug> / source:<name> that resolve against the catalog on every change — a newly tagged or imported channel joins the bouquet by itself. Removing a package (or a member) removes the grants only it covered; manual grants and auto-grant source channels are never touched. A viewer that already unsealed a key may have it cached — a hard lockout is a stream-key rotation. Registry lives in DATA_DIR/packages.json.

How publisher keys work

Each broadcaster site gets its own registration key, valid only for the channel ids its scopes match — a leaked key can no longer touch other sites' channels, and revoking one site is a status flip here instead of re-keying everyone. The secret is shown once at enrollment; put it in that site's broadcaster .env as PUBLISHER_KEY together with PUBLISHER_NAME. Registry lives in the panel-private secrets/publishers.json.

How sources work

A source pulls a provider-prepared JSON of channels on its interval and materializes it as a category of redirect channels — viewers play each entry's URL, no P2P feed. The feed is data only: entries are validated like admin input, and a source can never touch manual channels or another source's ids. Channels that leave the feed are removed (grants included). P2P channels tagged with the same category share the rail. Oversized feeds are capped (500 channels by default, sources.maxChannels) and invalid entries skipped — the report line under Last sync opens the full details. Registry lives in DATA_DIR/sources.json.

How the VOD provider works

A separate movies & series catalog the apps fetch directly from the provider — this panel never proxies its calls or its media, and it stores no viewer credential for it (each viewer authenticates with their own account). Everything here is public coordinates: the API base (https only, no query string, no embedded credentials), the provider's service and per-kind source values, plus extra query params passed through verbatim. Enabled is the switch: on, both apps show a VOD section; off — or never configured — the option does not exist for viewers. Changes apply at each viewer's next login. The two source values are independent: leave series source empty and the apps show Movies only — the Series menu item does not appear at all.

How categories work

Categories are stored on each channel as plain strings — that stays the wire format, so the apps need no change. This tab manages the vocabulary: display label, sort order, visibility, and bulk rename/merge. A two-level rail is written Parent/Child, and renaming a parent moves its children with it. Membership vs presentation: a source feed decides which channels carry its category and reasserts that on every sync — so to move an imported rail, rename the source's category on the Sources tab. Everything here (label / order / hidden) is yours and survives a sync.

Privacy and alert mechanics

Who reported this? Nobody knows from here — and that is deliberate. The panel verifies the viewer's session token, then immediately reduces the identity to HMAC(salt, user|device) sliced to 16 hex. That reporter pseudonym is all that is stored, deduped and counted; no username and no device id ever reaches this tab, the files, the notifications or the logs. Honest limit: the salt lives on this panel (DATA_DIR/secrets/reports-salt), so you could re-derive the mapping — it is pseudonymous at rest, not anonymous to the operator. Free text is written by the viewer and is rendered as plain text, never as markup. An alert opens when REPORTS_ALERT_COUNT distinct reporters hit one channel inside REPORTS_ALERT_WINDOW_MIN minutes, and pushes once to the configured webhook/Telegram targets (a dead endpoint is dropped after 3 attempts — it can never slow the panel down). During a storm only a bounded sample of full records is kept; the rest are counted on the alert, and reports past REPORTS_GLOBAL_PER_MIN are shed. REPORTS_RETENTION_DAYS=0 turns the whole feature off, including the RPC method.

What these numbers mean

What this is — and is not. Every number here is an aggregate count the panel already observes as a side effect of serving: login outcomes, session tokens issued, and how many peers hold the catalog connection. Per-user watch tracking does not exist in Aliran — viewers replicate streams peer-to-peer and never report what they watch, so there is nothing to show and nothing to leak. "Unique viewers" is the size of an in-memory set that is reduced to a count and discarded — usernames are never written to disk. "Apps online" counts panel swarm connections, which includes non-viewer peers (repeaters, broadcaster links) — treat it as approximate, and treat all peer counts as a lower bound (≥): viewers also serve each other. Rollups live in DATA_DIR/analytics/ (retention days; ANALYTICS_RETENTION_DAYS=0 disables collection entirely). See docs/analytics.md.

More about the pairing code

The panel calculates the code from its public key (). Thus there is nothing to create and nothing to expire — every panel start gives the same code. You can print the code on a card or an invoice. If you rotate the panel key, the code changes with it, so print it only on material that you can print again. The app calculates the code back from the key it receives and refuses a service that does not match.
